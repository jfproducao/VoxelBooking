# Node.js and Supabase migration

## Target architecture

- Node.js 22 and Fastify serve the web application on Render.
- Supabase PostgreSQL is the system of record. The Node service uses `pg` with parameterized SQL because booking concurrency, OAuth, and operation receipts rely on transactions and row locks.
- Configure `DATABASE_URL` in Render from Supabase **Connect → Session pooler** (port 5432). The direct `db.<project-ref>.supabase.co:5432` endpoint is IPv6-only on standard Supabase plans, while Render does not provide outbound IPv6; use direct only if the Supabase project has its paid IPv4 add-on. Copy the session pooler's host and username from the dashboard because they differ from the direct endpoint. Do not use transaction-pooler mode for migrations or code that takes session advisory locks.
- This project's Render pooler endpoint is `aws-0-us-west-2.pooler.supabase.com:5432`, user `postgres.drfislzpsmdxypzmsdqq`, database `postgres`. Set the real `DATABASE_URL` as a secret on both the Render web service and notification cron job, replacing the password placeholder with the Supabase database password. Percent-encode reserved characters in the password. The repository intentionally stores no password.
- Keep TLS certificate verification enabled. The project's CA certificate is stored at `config/prod-ca-2021.crt`; Render's web service and notification job set `DATABASE_SSL_CA` to this file, and `server/db/pool.js` reads it while verifying the certificate. The CA is public and is not a database credential, so include it in the deployment repository.
- PostgreSQL migrations are versioned SQL files in `server/db/migrations/` and run from Render's pre-deploy command. The initial schema preserves ULIDs as 26-character strings and PHP `DATETIME` values as timestamps without a timezone.
- Render uploads use Supabase Storage in the target design. The PHP version writes to its local `public/uploads/` folder; that folder is not safe storage on Render's ephemeral filesystem.
- Render Cron Jobs replace the PHP cron endpoint for scheduled work once the Node mail and maintenance jobs are ported.

## Data migration outline

1. Back up the MySQL database and uploaded media.
2. Apply the PostgreSQL baseline to a new Supabase project, then reconcile schema differences against a real MySQL export.
3. Set `MYSQL_URL` to a read-only account and `DATABASE_URL` to the empty Supabase project. Run `npm run db:import:mysql` first; it is a read-only dry run that checks source tables, PostgreSQL columns, required fields, and row counts. Keep MySQL writes stopped during a real import.
4. On an empty staging project, apply with `node scripts/migrate-mysql-to-supabase.js --apply --confirm-empty-target`. The importer preserves identifiers, DATETIME wall clocks, JSON, booleans, and decimal strings, imports tables in baseline dependency order, and checks row counts plus per-table SHA-256 content checksums inside each table transaction. It stops if any destination application table already has rows. If an import fails after earlier tables committed, recreate the empty staging database and repeat after fixing the reported schema/data issue.
5. Run `npm run db:verify:mysql` while the source remains frozen; this compares row counts and full content checksums for all baseline tables. Then compare business invariants, including bookings per tenant/status, customer links, event capacity, agent grants, receipts, and OAuth token expiry.
6. Run the Node application against staging and rehearse a final write freeze, import, cutover, and rollback before changing production DNS.

The migration tooling does not connect to a live Supabase project or move production data unless explicitly run with source/target credentials. No database credentials are stored in the repository.
